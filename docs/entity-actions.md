# Entity Actions

Entity actions let compiled app code expose callable operations on an Entity. Studio and the Record API invoke them after server-side permission checks.

Actions are Go code. dygo does not load Go files dynamically at runtime. A project runner must import app action packages and pass their registrars to the public runtime entrypoint.

## Entity Bundle Convention

Action source files live inside Entity bundles as `actions/actions.go`. The extra directory keeps the action package separate from Entity hooks in the same bundle.

```txt
apps/crm/
  app.yml
  entities/
    lead/
      lead.entity.yml
      actions/
        actions.go
```

Collections do not get standalone action scaffolds by default. Parent Entity actions own collection row behavior.

## Generate Actions

Create the action file and project runner wiring with:

```sh
dygo generate action crm/lead
```

The command expects `<app>/<entity>`, where `<app>` is the app manifest `name` and `<entity>` is an Entity in that same app. It creates `entities/<entity>/actions/actions.go` when missing and creates or updates the project-local `cmd/dygo/main.go` runner.

After generation, edit the Entity action file and run dygo through the project runner:

```sh
dygo dev
```

`actions.go` is developer-owned after creation. dygo does not overwrite custom action logic. `--force` refreshes generated runner wiring only.

If `cmd/dygo/main.go` already exists and was not generated by dygo, the command refuses to overwrite it and prints the manual wiring needed.

`dygo hook sync` updates generated runner wiring when an action package is added or removed. It does not create action files. `dygo hook validate` and `dygo doctor` report missing `Register` functions and stale runner wiring.

## Registration Shape

An Entity action file exposes one `Register` function and registers actions for its matching Entity.

Actions register by app-scoped Entity identity, not by route slug.

```go
package actions

import (
	"context"

	"github.com/hapyco/dygo/pkg/dygo"
)

func Register(registry dygo.EntityActionRegistry) error {
	return registry.RegisterEntity("sales", "lead", dygo.EntityActionDefinition{
		Name:      "lead-action",
		Label:     "Lead Action",
		Selection: dygo.ActionSelectionRecord,
	}, runLeadAction)
}

func runLeadAction(ctx context.Context, call dygo.EntityActionCall) (any, error) {
	return nil, nil
}
```

Add more `RegisterEntity` calls in the same file when one Entity needs several actions. Keep each action name kebab-case and unique on that Entity.

Selection chooses how many Records the action accepts:

- `dygo.ActionSelectionRecord` requires one Record.
- `dygo.ActionSelectionSelection` requires one or more Records.
- `dygo.ActionSelectionCollection` accepts no Record IDs.

The generated project runner imports each Entity action package and calls dygo through `pkg/dygo/runtime`:

```go
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"syscall"

	crmleadactions "example.com/my-project/apps/crm/entities/lead/actions"
	"github.com/hapyco/dygo/pkg/dygo"
	dygoruntime "github.com/hapyco/dygo/pkg/dygo/runtime"
)

func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	err := dygoruntime.Run(ctx, os.Args[1:], os.Stdin, os.Stdout, os.Stderr, dygoruntime.Options{
		EntityActions: []dygo.EntityActionRegistrar{crmleadactions.Register},
	})
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
}
```

## Runtime Contract

Entity actions run inside one server transaction. The handler receives the actor, selected Record IDs, raw input, and transaction-scoped Records, Jobs, Files, Timeline, and Notifications services.

Permissions stay on the server. The compiled action cannot bypass Record or Entity action authorization.

Return `dygo.ActionError` when the handler needs a stable HTTP error code and message.

See [App SDK](sdk.md) for the public types.
